# Changelog

## 0.8.4

- **Dashboard: every increment the project knows about is shown.** Until now the page built its increments from the `## Increment <n>: <title>` headings of `BACKLOG.md` and added only increments `MILESTONES.md` lists as closed. A project whose `prepare` wrote the later increments under one range heading (`## Increments 2 to 5`, seen in a field run on 0.8.3) lost them from the page while `FEATURES.json` rows and `NEEDS-HUMAN.md` acts still pointed at them. The page now shows one fold per increment named by a `BACKLOG.md` section, a `MILESTONES.md` increments row, a `FEATURES.json` row (`3` or `"3"`) or a `NEEDS-HUMAN.md` increment number, whatever its state. One without a section renders from what is known: title and exit demo from `MILESTONES.md`, rows and pass counts, human acts, "slices not cut yet", a "no BACKLOG section" chip and the files that name it. A heading that names increments in another form gets a banner naming it, and another banner lists the increments without a section. Increments closed before adoption keep their handling; that now applies only to closed `MILESTONES.md` increments numbered below every `BACKLOG.md` section, so a closed increment after adoption is no longer labelled "before adoption".
- Progress tile rule: an increment with neither slice rows nor proposed slices is not sized. It is left out of the percentage (counted neither as done nor as remaining, where it used to count as one guessed slice) and shown hatched at the average increment size. The number then reads "% of sized", and the tooltip and the budget forecast say which increments are not counted.
- `check-design-docs.py` gains check 6: `BACKLOG.md` has one `## Increment <n>: <title>` section for every `MILESTONES.md` increment and every `FEATURES.json` and `NEEDS-HUMAN.md` increment number, and no increment heading in another form. Pre-adoption closed increments are exempt.
- The rule lives in method chapter 14 (Plan), and chapter 9 describes the page. The `BACKLOG.md` template shows a sliced and a not-yet-sliced section with a `Proposed slices (candidates): a; b; c.` line, and forbids range headings. `prepare` (0.5.1) writes a section per increment, however far ahead; `kickoff` (0.5.1) and `refocus` (0.6.1) follow the template. `plan-increment` (0.5.1) replaces the candidates line with the slice table, and `retro` (0.5.1) requires the next increment's section before starting it.
- Tests: a third dashboard fixture (`increments`: a range heading, increments known only from `MILESTONES.md`, from `FEATURES.json` and from `NEEDS-HUMAN.md`, and the normal case), with the 0.8.3 algorithm kept as a negative control that fails the same checks. Four lint tests, including a control showing that the five earlier checks pass the defective fixture.

## 0.8.2

- **Security: adopters must take 0.8.2.** The 0.8.0 and 0.8.1 Codex writer roots exposed the whole main `.git` directory. A sandboxed writer could plant executable Git configuration or hooks that an unsandboxed coordinator, collector or gate runner would later execute, and could move other branches. Do not adopt either version's writer roots.
- `writer_roots.py` replaces that grant with only the linked worktree's Git directory, the object store, exact own-branch ref/reflog files and their locks, plus configured output/run directories. The host prepares only the assigned branch's parent directories after ref packing. The dispatcher refuses foreign/main worktrees, integration branches, allocation branch mismatches, symlinked metadata paths and artifact roots that expose Git metadata. It never grants `refs/heads` as a whole, config, hooks, info, packed refs or another branch.
- Host Git calls in the collector, gate runner, launcher, agent generator and hooks use `-c core.fsmonitor= -c core.hooksPath=/dev/null` through the shared Python or shell helper. The worker supervisor has no direct Git invocation. Regression fixtures prove planted fsmonitor and pre-commit code executes without the overrides and does not execute with them.
- A reproducible live probe on installed CLI `0.162.0-alpha.17.2` uses its standalone `app-server` `command/exec` sandbox with the dispatcher's settings, without a model turn. On both loose and packed refs, add/commit succeeds on the slice branch while seven protected write attempts are refused, including config, hooks and the integration ref. The adapter records exact commands, the root list, the packed-ref preparation and denied maintenance warning. Hook and Python suites retain all previous cases.

## 0.8.1

- Project-owned hooks can suppress all six package enforcement entry points with `SW_PLUGIN_HOOKS=off` (default `on`); session context remains available. Copy adoption documents disabling the plugin in the project settings as well, to remove duplicate skill names.
- Codex writers keep network access disabled. `SW_CODEX_NETWORK=1` and unverified `local` modes now fail closed; security overrides in `SW_CODEX_EXEC_ARGS` are refused. The installed CLI's local-proxy probe could not establish local TCP isolation, so `gate-runner.sh` and its deterministic host supervisor broker a T1 request file through the configured project verifier and its existing verification-slot admission, returning a result and log without a model turn.
- Before HOLD or CANDIDATE, implementers run lint and all database-free tests for changed packages through `SW_PREHANDOFF_CMD` (empty defaults to T0), and report commands, results and logs. The Stop gate checks HOLDs too; an unavailable-command exemption requires the exact command and captured output. Candidates retain their original T0 gate.
- `SW_CODEX_BIN` selects the CLI (default `codex` on PATH), with macOS bundle guidance on failure. The dispatcher records allocation PIDs and thread ids while a worker is live, uses `sandbox_mode` for resume (the installed CLI has no resume `-s`), and refuses writers in the coordinator checkout. Worker metrics land under the run directory via `SW_TIERS_FILE` and `SW_METRICS_DIR`; the coordinator imports complete rows idempotently with `collect.py --merge-worker-metrics`.
- The runtime adapter records CLI `0.162.0-alpha.17.2`, the exact attempted network keys, the fallback protocol and migration requirements for project-owned verifiers and dispatchers. Hook and runtime regression tests cover these paths.

- `scripts/runtimes/codex/agents.py`: the agent profiles rendered as `.codex/agents/*.toml` (`sync`), the parity check for T0 (`check`, content only), and one field for the launcher (`show`); the implementer is never a native subagent. - A Codex native child spawned without a role reports `agent_type: "default"`; the hooks treat that as no role, so inside a worker it keeps the worker's guard. A worker session opens with a worker paragraph from `session-context.sh` (role and allocation), never the coordinator's. The design note `docs/design/2026-10-15-context-isolation.md` records how history and other context reach workers on both runtimes and plans the fix in phases.
- `install.sh --tools codex` generates the agents and, with `--hooks`, `.codex/hooks.json` for a copy install. `adopt` (dual profile), `resume`, `brief`, the agent-guide fragment, `templates/codex-config.toml` (no hard-coded thread cap) and method chapter 10 point at the adapter. Twenty-three more hook cases cover Codex-shaped input, the role marker and the continue loop; Python tests cover the agent sync and the launcher with a stand-in `codex`.
- The GitHub account was renamed from `glotyuids` to `sudo-sane`. The plugin manifest (author, homepage, repository), the install commands and Codex marketplace source in the README, the schema `$id`s, the method links and every skill's `metadata.source` now name `sudo-sane`. Skill versions are unchanged except `update`. The frozen design notes in `docs/design/` keep the old name; GitHub redirects it.

## 0.7.0

- Dashboard: the package now ships the generator (`dashboard/`, standard library only, collect → compute → render), ported from the first run's page with its tokens, CSS and components unchanged: progress, scenario, budget and money tiles, hold banners, one fold per increment with a segmented bar, a timeline and slice cards with a six-step stepper, the owner's inbox, veto clocks, open questions and milestones. Until now an adopting project had to write its own page, so every project looked different and a published copy was restyled. Everything project-specific moved into configuration (`SW_PROJECT_NAME`, `SW_DASHBOARD_OUT`, `SW_DASHBOARD_PUBLISH_CMD`, `SW_DASHBOARD_PUBLISH_EVERY`; `SW_TIMEZONE` now accepts offsets); the first run's legacy block, code-size baseline and budget-card variants were dropped.
- The slice-state vocabulary is defined once, in `dashboard/compute.py` (stage, colour and progress credit per state, including `paused`, `stopped`, `hold`, `waiting`, `green`, `cut`). A state outside it renders `UNKNOWN <state>` with a banner. Cut slices leave the progress total. Increments that `MILESTONES.md` lists as closed before adoption show as closed folds and a separate "before adoption" segment, and are not counted. Tables with empty cells (`| |`) parse, and slice ids may carry a name (`slice-01 land-inflight-set`).
- `scripts/dashboard-loop.sh` rebuilds the page every 30 seconds, stops on the kill switch and runs the project's publish command. `scripts/install.sh <project> --dashboard` copies both into `scripts/sliceworks/`. `adopt` installs and renders it and forbids project-written or restyled dashboards. `resume` and the START template name the loop command. Method chapter 9 describes the page and its rules, including that a shared copy is the generated file byte for byte.
- Thirty-two dashboard tests on two fixture projects (one mid-run, one freshly adopted with money and named slices) check the parsed page structure and the computed numbers.
